Library reference: python/

Generated from the code by tools/build_library_reference.py; do not edit by hand. Rebuild it after changing a function.

The pulse-analysis library, the Python package goldpan (in python/). Background and history: Note 1a and Note 4. Import a module as from goldpan import cuts; the library is installed by requirements.txt (see python/README.md). The old flat names (pulse_cuts and the others) are aliases of these modules with the Run 76 readout as the default config, kept for the existing notebooks. In this package every function takes a readout (config) and has no default for it: name your data's readout with goldpan.config.DCRC_RUN76, goldpan.config.Z7 or your own PulseConfig. Samples are on the last axis, so every function takes one pulse or a whole batch. A function marked under development still runs but emits a UserWarning on every call.

goldpan.config

Configuration of a readout, shared by the pulse quantities, cuts and operations.

One PulseConfig is passed explicitly to every function in goldpan.quantities, goldpan.cuts and goldpan.operations. It has no defaults: how long the pretrigger window is, how many leading samples carry a glitch and how long one sample lasts all belong to a readout, not to this library, and a wrong silent default (the library once assumed 1.6 us for a readout that samples every 0.8 us) changes every time, frequency and energy without any error. Name the readout of your data, either with a preset or with the numbers:

from goldpan.config import DCRC_RUN76, Z7, PulseConfig
config = DCRC_RUN76                                                  # the Run 76 phonon channels
config = PulseConfig(pretrigger_samples=2000, glitch_samples=10, sample_period_s=1e-6)   # your own

The presets are data, not recommendations: DCRC_RUN76 is the DCRC readout of the Run 76 (UMN, 2022) series, 0.8 us per sample (1.25 MHz; see "The sample period" in python/README.md for the evidence), and Z7 is the Z7 (SNOLAB) readout, 1.6 us per sample (625 kHz). Both are right for their data and wrong for each other's.

PulseConfig(pretrigger_samples: int, glitch_samples: int, sample_period_s: Optional[float]) -> None

goldpan.quantities

Derived quantities: pulses in, one real number (or one array) per pulse out.

Every function here takes an array shaped (..., n_samples) -- a single pulse (n_samples,) or a batch (n_pulses, n_samples) both work unchanged, since all reductions run along axis=-1. Output shape is one dimension smaller ((...,)) for scalar-per-pulse quantities, or (..., n_freq) for spectra.

These are the primitives: cuts in goldpan.cuts are built by thresholding the quantities defined here.

goldpan.cuts

Cuts: pulses in, one boolean per pulse out (True = keep).

Every function takes an array shaped (..., n_samples) and returns a boolean array of shape (...,). Cuts are plain functions of the quantities in goldpan.quantities -- combine them with ordinary &/|/~ rather than a special combinator API.

randoms and real_triggers are the exception: they take an array of trigger-type labels (see goldpan.io.trigger_types), not pulses, since that is per-event metadata.

Percentile-based cuts (quiet_baseline, excursion_below_percentile) compute the percentile from the batch passed in, i.e. "quiet relative to this population" -- pass the same batch you're about to select from, not some other reference set, unless that's actually what you want.

goldpan.archive

Persistent archive of "good event" selections, keyed by series/detector/channel.

Every cut in goldpan.cuts is cheap to recompute from raw data, so this isn't a cache -- it's a durable record of which detector_ids a particular cut (run with particular parameters, on a particular dump) actually selected, so a later notebook or a re-run with different library code can compare against what was kept before, without re-deriving it from scratch or re-reading notebook output by hand.

One HDF5 file, one group per (series, detector, channel):

/<series>/detector<N>/channel<C>
dataset "detector_ids"   -- variable-length UTF-8 strings
attrs: cut_name, cut_status, cut_params (JSON string), n_total,
       n_kept, dump, pretrigger_samples, glitch_samples,
       sample_period_s, source_notebook, created (ISO 8601, UTC)

Saving a group overwrites it -- the archive holds the current good-event list per series/detector/channel, not a history of every past run. Only this module knows about h5py; everything else in python/ stays free of that dependency.

goldpan.channels

Which physical detector channel is a dump's (detector, channel) pair?

A dump labels its traces <event>_<detector>_Phonon_<n> and holds 4 channels per detector, so a trace is addressed by two small integers: detector (0, 1, 2) and channel (0 to 3). In Run 76 those are not three detectors but three 4-channel readout boards (DCRC1, DCRC3, DCRC4) of one two-sided detector, and the real channel names are Side1pA ... Side1pF, Side2pA ... Side2pF. This module turns the two integers into those names:

from goldpan import channels as pch
pch.channel_name(0, 0)      # 'Side2pC'
pch.channel_label(0, 0)     # 'Side2pC (DCRC1 pA, HV2 pA)'
pch.channel_info(0, 0)      # Channel(detector=0, channel=0, name='Side2pC', ...)
pch.find_channel('Side2pC') # (0, 0)
pch.all_channels()          # the 12 Channel records, in (detector, channel) order
pch.sensor_channels()       # the 6 that are QET channels of the detector

Which table to use. The Setup table of the Run 76 summary (https://villano-lab.github.io/R76Analysis/cdms/k100/run_summary/run_76.html; Matt Fritts's explanation of it is on page 28 of notebook N-MISC-23-001) gives, for every sensor Label, the HV connector pin it is wired to in Side-1 readout and in Side-2 readout. HV1 and HV2 are the two D-sub connectors the DCRCs plug into (HV1 is DCRC3, HV2 is DCRC1; the 2022 run diaries' header says "HV 1(L)/2(R) -> DCRC50(3)/DCRC55(1), ... NaI trigger signal -> DCRCX(4)"), and pin pA ... pD of a connector is input pA ... pD of its DCRC. The table's DCRC (2-sided) column is for the two-sided readout and is not used. The run was in Side-2 readout from late in the Run 76 diaries, so the December 2022 series (07221203_2025) is Side-2 readout, the default here (readout=2). In Side-2 readout only the pins A, B and D carry sensors (pC is for Side-1 readout) and DCRC4 pA carries the trigger signal of the NaI array, so six channels are sensors, one is the NaI trigger input and five are not connected. (For DCRC1 the table's A/B order is the one used; the explanatory text next to the table has A and B the other way round, which is taken to be a typo.)

Only this module knows the table; everything else in python/ works on plain arrays and indices.

The mapping is under development: that the dump's detectors 0, 1, 2 are DCRC1, DCRC3, DCRC4 (ascending board number) is inferred, and that channels 0 to 3 are the board inputs pA to pD in order is assumed. If they turn out wrong, change DCRC_OF_DETECTOR or the order of the rows in PINS and nothing else.

History. Until 2026-10-22 this module used the table's DCRC (2-sided) column and named twelve sensors on both sides, which was wrong for Side-2 readout (six of its "Side 1" channels do not exist in the readout of this series).

goldpan.data

The in-memory container of one detector's events: traces, quantities, readout, provenance.

This is the middle of the design in GoldpanGoldsluice/2026-10-25 (log repository): file formats live in adapters, the functions of goldpan are pure, and what passes between them is an Events, immutable. The simplest version is built first: one detector, and the traces of a channel are held in named segments (here only the default, "main"), so that hybrid sampling later (a coarse and a fine segment) changes no signature and no file.

An Events has

  • a Detector: its name, its channels (name, role, the readout unit and input they come through) and its Readout (the segments of a trace, each with a PulseConfig);
  • traces: {(channel, segment): array of shape (n_events, n_samples_of_the_segment)}, read-only (use ev.trace(channel));
  • quantities: an Awkward Array, one record per event. Its first fields identify the event, series, dump and event (event numbers restart in every dump), and t_trigger (seconds on the clock named in meta["clock"]) may follow; the rest are the quantities (RQs). Flat numbers and variable-length lists are both fields.
  • meta: provenance (source files, program versions, units of the quantities, the clock).

goldpan.adapters.idx

The idx adapter: a dump of the NSDF archive (NEXUS-DM idx) into an Events. Read only.

An idx dump numbers its traces by readout board and input, not by channel name: a trace is addressed by an id like <event>_<board>_Phonon_<n> and a channel of it by a small integer. In Run 76 the three "detectors" of a dump are three boards of one physical detector. This adapter hides that: you say which board and input each named channel comes from, and you name the readout, because neither belongs to the library:

from goldpan.adapters import idx
from goldpan.config import DCRC_RUN76
ev = idx.read("~/idx/07221203_2025_F0001", detector_name="S104", config=DCRC_RUN76,
              channels={"Side2pC": (0, 0), "Side2pF": (0, 1)})          # channel name -> (board, input)

For Run 76 the map of every sensor is in goldpan.channels (sensor_channels()). Only this module and goldpan.io know nsdf_dark_matter's cdms object; it is imported when a path is given, so tests can pass any object with get_detector_ids(), get_detector_channels(id) and get_event_metadata(event).

goldpan.adapters.parquet

The native format of goldpan and goldsluice: Parquet (specification, format version 1).

goldsluice writes it, goldpan reads it, and anything else can read it: the files use plain Arrow types, not extension types, so Polars, DuckDB, pandas and pyarrow open them without goldpan. The design is in GoldpanGoldsluice/2026-10-25 and 2026-10-26 (log repository); this docstring is the specification.

A dataset is a directory:

<dataset>/
_goldpan.json                      the manifest
<detector>/<series>_<dump>.parquet one file per series dump of a detector

The manifest is JSON: {"format": "goldpan-dataset", "format_version": 1, "streams": {<detector>: {"kind": "events", "main_array": true, "detector": {...}, "files": [relative paths]}}}. A stream is the table of one detector; only streams of kind events exist so far (time series and ancillary streams are added later without changing this). A single .parquet file is also a valid dataset for the reader.

A file is the table of one detector's events, one row per event, with these columns:

  • series (string), dump (string), event (int64): the key that identifies an event (event numbers restart in every dump).
  • t_trigger (float64, optional): the trigger time in seconds, on the clock named in the metadata key clock.
  • traces.<channel>.<segment>: a fixed-size list column per channel and segment (the samples of one trace), any numeric dtype; segment is main for an ordinary trace. Channel and segment names contain no dot.
  • every other column is a quantity (an RQ): a number, a string, a list of numbers (variable length is fine), or a struct of these (for example a struct per channel with std and max).

File metadata (Parquet key-value, all strings): goldpan.format_version (an integer; a reader refuses a newer one), goldpan.detector (JSON: name, channels with name, role, unit, input, and segments with name, n_samples, pretrigger_samples, glitch_samples, sample_period_s, start_s) and goldpan.meta (JSON: provenance, units of the quantities, the clock). Compression is zstd; row groups hold a few hundred events, so that a reader can skip groups and read only some columns.

Versioning. An addition that old readers can ignore (a new quantity, a new metadata key) keeps the version; a change they cannot read raises goldpan.format_version. The sample dataset in python/tests/data/sample_dataset/ is read by the tests of goldpan and is the file that goldsluice's tests read too.
