Why a library

Three notebooks had each grown their own copy of the same handful of computations (pretrigger mean and standard deviation, the excursion ratio, baseline subtraction, an FFT power spectrum), with the same constants hardcoded separately in each. That logic now lives in one place, and the notebooks import it. Refactoring reproduced the notebooks’ earlier numbers exactly (bstd_cap = 32.48, ratio_thresh = 1.93, 41 of 1517 traces for the first noise cut; 10 of 11,642 for the triggered-pulse cut).

Framework

  • Samples on the last axis. Every function takes an array shaped (..., n_samples): one pulse (n_samples,) or a batch (n_pulses, n_samples) both work, because every reduction runs along axis=-1. A plain NumPy array is the pulse; there is no custom class.
  • One shared config. A frozen dataclass PulseConfig (pretrigger_samples = 1000, glitch_samples = 10, sample_period_s = 1.6e-6) is passed explicitly to every function, replacing the constants copied between notebooks.
  • Three categories, one contract each. Quantities return one number (or spectrum) per pulse; cuts return one boolean per pulse and combine with plain &, |, ~; operations return new pulses and never modify their input.
  • Flat modules, no package. Imported by inserting python/ into sys.path, the same convention as nrFanoII_paper2022’s python/ba_bknd_lines.py.
  • Only two modules touch outside systems. pulse_io.py is the only one that knows about nsdf_dark_matter’s cdms objects; pulse_archive.py is the only one that needs h5py.

Marking functions done or under development

Every function is tagged @status(DONE) or @status(UNDER_DEVELOPMENT, note=...). An under-development function still runs, but emits a UserWarning carrying its note on every call, so a notebook that depends on one says so in its own output instead of looking as settled as everything else. list_statuses(module) returns the inventory. Currently 24 done and 5 under development across 29 tagged functions.

Validation

There are 40 synthetic-data unit tests (no dependence on real detector data or nsdf_dark_matter), all passing. One of them began life with a wrong expected value and, once corrected, became a regression test for the pretrigger-contamination effect of Note 2: a spike confined to the pretrigger window drags the baseline mean far enough that flat post-trigger samples end up looking like the largest excursion. Tests run under the base conda environment (pytest is not installed in darkmatter_cli_env): cd python && python -m pytest tests/.

Naming change on 2026-09-23

The original generic excursion_band(low, high) thresholded the linear ratio. To free the name for the specific log10(ratio) cut, the generic function was renamed ratio_band; its one caller, the ratio > 9 cut in Note 5, was updated and re-run to confirm it still selects the same 10 traces.

Status / Next Steps

  • Five functions are still under development; see their status notes for what is not yet checked.
  • Thresholds such as the default min_duration = 50 were chosen on one dataset (Detector 0 / Channel 0, dump 1) and need re-checking elsewhere.
  • A proper normalized one-sided PSD quantity is missing (see Note 3).
