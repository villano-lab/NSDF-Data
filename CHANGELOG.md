# Changelog

All notable changes to this repository are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [semantic versioning](https://semver.org/) (see `RELEASING.md`).

## [Unreleased]

### Added

- **Code blocks in student notes have a Copy button, and a click on a picture opens it in its own tab.** This is `docs/notes-extras.js`, loaded by the generated note pages (the pages are rebuilt on the next push that changes a note or the build tool).
- **A student note shows when it became Complete, and when it was revised.** The front-page row and the note's own page now say *Complete (2026-09-14)*: the day the note was first published as Complete, taken from Git's history by `tools/build_notes.py` (following first parents, so a merged pull request counts as the day of its merge). If the note goes back to another status and is published as Complete again, they say *Complete (2026-09-14), revised (2026-10-01)*, and the page gets a red box *Revised (date)* at the top, unless its author has already put a box there that starts with **Revised.**, **Correction.**, **Revision.** or **Update.** Nothing is shown if the history is not there (a shallow clone), so the notes build now fetches the full history. Hand-written notes keep their dates by hand. 17 tests in `python/tests/test_note_completion.py`; guide 3 (version 22) says it.
- **Formulas in student notes are drawn on the published page.** Write them in LaTeX between `$...$` (inline) or `$$...$$` (an equation): `tools/build_notes.py` now runs pandoc with `--mathml`, so the browser draws them as MathML, with no script or CDN to load, and VS Code's Markdown preview draws the same text. `docs/style.css` gives a display equation some margin and a sideways scroll on a narrow screen. `tools/check_note_numbers.py` does not look inside formulas (a dollar amount such as "$5 and $7" is not a formula, as in pandoc). Guide 3 (version 21) has a section *Formulas*. 5 tests in `python/tests/test_note_math.py`.
- **The next note number is suggested on the pull request of a student note.** When a note still has `id: "TBD"`, the *Student notes* workflow runs `tools/suggest_note_number.py`, which posts a review comment on that line with the next free number (`build_notes.py next`, on the pull request merged into `develop`) as a suggestion block. The reviewer presses **Commit suggestion** and merges, with no checkout; the commit is the reviewer's, so the checks run again. Nothing is pushed to the student's branch. A re-run updates the comment if the number changed; if GitHub refuses a line comment it posts an ordinary one. 10 tests in `python/tests/test_suggest_note_number.py`. The developer quick-sheet *Creating a note* (version 6) says how to use it.
- **`tools/check_note.py`: one command for all the checks on a student note.** `python tools/check_note.py notes/src/your-note.md` runs the structure check (`build_notes.py check`), the pinned-link check (`check_note_pins.py check`) and the number check (`check_note_numbers.py`), and shows only what concerns that note, with one result at the end. A problem in the structure or the pinned links fails it (exit status 1); the number check is advice, and fails it only with `--strict`. `--changed REF` checks the notes changed since a Git ref, `--only` and `--skip` choose the checks, and `--github` writes the result for CI. A new check for notes is added to this one tool. 14 tests in `python/tests/test_check_note.py`.
- **`tools/check_note_numbers.py` lists the numbers in a student note that are not in its notebook's output.** Run `python tools/check_note_numbers.py notes/src/your-note.md`: it reads the notebook(s) the note links to (at the pinned commit), and reports each number in the text, captions included, as found in the saved output, found only in the code (an input you chose), or NOT FOUND. Numbers match at the digits the note shows (0.52 for 0.5213), as percents, and as rounded whole numbers (5200 for 5213.4); header, code, links, labels ("Figure 1"), dates, years and references are skipped, and a line ending in `<!-- numbers-ok -->` is skipped. It is a checking aid, not a gate (exit status 1 if anything is NOT FOUND). Tests in `python/tests/test_check_note_numbers.py`.
- **Pinned links in the notes are checked, and each shows a "latest" link (issue 51).** Notes link to files at an exact commit, so the numbers stay tied to the code that produced them; that left readers with an old version of a file and, after the `data_analysis/` move, links to paths that no longer exist. New `tools/check_note_pins.py` and a CI workflow, *Note pins*: `check` fails if a pinned link in any note (hand-written or student) does not resolve, or is not pinned to a commit hash; `report` lists, for each note, which pinned files are unchanged, changed (how many commits and when), moved or removed since, for the maintainer: it can be run by hand at any time, appears in the summary of every run, and every Monday is posted as a comment on a standing issue (assigned to the maintainer, and only when the list has changed). Every note page loads `docs/notes-pins.js`, which adds a small [latest] link after each pinned link, pointing to the same file on `develop`, or to its new place when it has moved (`docs/notes/pin-moves.json`, written by `report --write-moves`; CI warns when it is out of date). The 25 pinned links in the 9 notes that have them all resolve today; 14 of the files have moved and 10 have changed. Notes marked Complete get only the one script line.
- **Developer quick-sheet: reviewing a pull request.** One page for the maintainer and reviewers: the frame of a review (base, checks, files changed, an out-of-date branch and the *Update branch* button), what to read for each kind of PR (student note, student guide, library, hand-written note, CI or tools, release), how to word the comments, and how to merge (assign a note's number, merge commit, check the live page, clean up, what an agent may and may not do). It is in `docs/developers/` with the other quick-sheets and linked from the front page.

## [0.6.0] - 2026-10-13

The student guides gain *Updating your setup* and an environment check, the note guides now suggest VS Code and fully support Word and Google Docs (with a converter that carries the pictures), all notes share one table and one set of note numbers, and the library gets a channel-name module, a generated reference page and its own CI workflow.

### Added

- **A generated library reference page, `docs/library/index.html`.** `python tools/build_library_reference.py` reads every `python/pulse_*.py` module and writes one page with each module's docstring, its classes and fields, and a table of its public functions (signature, one-line summary, expandable details, and the `done` or `under development` tag with its note). It is separate from Note 1a, which keeps its history and prose and can be updated or superseded later. The front page links to it. `python/tests/test_library_reference.py` fails when the page no longer matches the code, and `test_library_conventions.py` now also requires a docstring on every public function (the library tests run when the generator or the page changes).
- **`python/pulse_channels.py`: which physical channel is a dump's (detector, channel)?** `channel_name(0, 2)` gives `'Side1pC'`, `channel_label` adds the DCRC board and tower input for plot labels, `find_channel` goes from a name back to `(detector, channel)`, and `all_channels()` lists all 12. The dump's three "detectors" are three readout boards (DCRC1, DCRC3, DCRC4) of one two-sided detector; the table comes from the Run 76 Setup table on the UMN wiki. Tagged `under_development`: that detector 0, 1, 2 are the boards in ascending order is inferred from a raw MIDAS file of another Run 76 series, and the channel order within a board is assumed. 11 new tests (73 in all).
- **Library tests run on their own in CI, and two rules of `AGENTS.md` are now tests.** The new workflow `.github/workflows/library-tests.yml` runs `python -m pytest` in `python/` on Windows, macOS and Linux for every pull request or push that touches `python/` or `requirements.txt`, so a broken function fails a check named after the library (the guide walkthrough in `check-instructions.yml` still runs the tests as Setup Step 6). `python/tests/test_library_conventions.py` fails when a public function in a `pulse_*.py` module has no `@status` tag, or when no test file mentions it (14 new tests, 87 in all).
- **Updating your setup (new student guide 7, for Windows, macOS and Linux), a Routine maintenance box, and an environment check.** Students had no way to find out that the guides moved to a new Python or new packages. `python/check_environment.py` (stdlib only; `check()` in a notebook or `python check_environment.py` in a terminal; warning only, `--strict` for CI) compares the Python version and the pins in `requirements.txt` with what is installed and points to the new guide. The guide covers the three cases: merge the newest changes into your branch, reinstall `requirements.txt` when packages changed, and make a new environment (save a list of the old packages, `conda env remove`, then `conda create`) when Python changed. A red **Routine maintenance** box says this is regular, not one-off: on the front page (with a new column in the guides table), at the end of the setup guide (version 18), in the first-analysis guide's *Before you start* (version 18), and at the top of the new guide. The first-analysis guide's Step 4 cell now runs the check. The library has 10 new tests (62 in all; the guides now say `62 passed`; Codespaces guide version 6). `RELEASING.md` says a release that changes the environment must start with a "Students, please:" line; CI runs the check in the environment the guide builds.
