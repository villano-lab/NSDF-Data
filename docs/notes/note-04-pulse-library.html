python/ pulse library: development history and validation

Note 4 · Author(s): Anthony Villano · 22 Sept 2026 · Status: In progress

How the library came about, what changed when, and how it was checked. What the library is — the modules, the function tables with their status, and the done / under-development convention — is in Note 1a.

Code Repository

  • python/ — the library and its tests. Pinned to 085aa3d.
  • python/tests/ — the unit tests. Pinned to 085aa3d.

Why it was written

Three notebooks (07221203_2025_dump1_noise.ipynb, 07221203_2025_dump2_pulse.ipynb and good_pulses_overlay.ipynb) had each grown their own copy of the same handful of computations, with the same constants (PRETRIGGER_SAMPLES, GLITCH_SAMPLES) hardcoded separately in each. The request was for a reusable library of pulse operations, cuts and derived quantities with a uniform input for every category.

Validation

Refactoring reproduced the notebooks’ numbers

After each notebook was switched to the library it was re-run end to end and its printed results compared with the earlier ad-hoc version:

  • first noise cut on Detector 0 / Channel 0: bstd_cap = 32.48, ratio_thresh = 1.93, 41 of 1517 traces (Note 2);
  • triggered-pulse cut over dumps 2–5: 10 of 11,642 traces (Note 5);
  • good_pulses_overlay.ipynb picked up one small intentional change from adopting the shared PulseConfig: its baseline now also skips the leading glitch samples, like the other two. Re-running showed a negligible effect on its already-quiet traces.

Unit tests

There are 43 synthetic-data unit tests (no dependence on real detector data or nsdf_dark_matter), all passing. They run under the base conda environment, since pytest is not installed in darkmatter_cli_env: cd python && python -m pytest tests/. h5py was installed into darkmatter_cli_env on 2026-09-23 for the archive module.

One test began life with a wrong expected value and, once corrected, became a regression test for the pretrigger-contamination effect of Note 2: a spike confined to the pretrigger window drags the baseline mean far enough that flat post-trigger samples end up looking like the largest excursion.

Checks on real data

The new cuts were checked against real Detector 0 / Channel 0 data, not just synthetic tests. excursion_band and excursion_band_loose reproduced the notebook’s inline masks exactly (192 and 744 of 1517). The first version of excursion_duration passed its unit test but failed on real data, flagging every trace of the Tight cut as a pulse, and was replaced by the consecutive-run definition (details in Note 6).

Naming change on 2026-09-23

The original generic excursion_band(low, high) thresholded the linear ratio. To free the name for the specific log10(ratio) cut, the generic function was renamed ratio_band. Its one caller, the ratio > 9 cut in 07221203_2025_dump2_pulse.ipynb (Note 5), was updated and re-run to confirm it still selects the same 10 traces. An early attempt to edit that notebook programmatically silently did nothing (the cell source was a single string, not a list of lines) and was only caught because the re-run failed.

Status / Next Steps

  • Thresholds chosen on one dataset, such as the default min_duration = 50, need re-checking on other channels, detectors and dumps.
  • Add a normalized one-sided PSD quantity (see Note 3).
  • Add a drift or slope quantity so a cut can tell a drifting baseline from a pulse (see Note 5).
