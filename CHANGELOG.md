# Changelog

All notable changes to this repository are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [semantic versioning](https://semver.org/) (see `RELEASING.md`).

## [Unreleased]

### Fixed

- **`goldsluice run` redoes an output when an algorithm or the reader it was made with has changed, and only then (issue 172).** A file was skipped when its fingerprint (the definition) and its stamp (the raw file) were unchanged, so a fixed kernel or reader changed nothing for outputs that already existed. Every algorithm of `goldsluice` now has a `REVISION` (a whole number, 1 when it is new), and every reader of `goldpan.adapters` may have one (`goldpan.adapters.revision`, 1 if absent); a fix that changes what one gives for the same input raises its revision by one, in the same pull request. The ledger records the revision of each algorithm the definition uses and of the reader of the source, and a file is skipped only if those are unchanged too; otherwise the run says `redoing <file>: algorithm peak revision 1 -> 2`. Adding an algorithm, fixing one the definition does not use or releasing a new version of a package changes nothing; adding a step to the definition processes the file again, because the definition changed (the per-step cache of issue 172 would avoid that). The versions of `goldsluice` and `goldpan` are still recorded, for information. A ledger written by the version-based check (it has `versions`, no `revisions`) counts as revision 1 everywhere, so nothing is redone for it; one written before that is redone once.

- **`goldpan.rqdata.load` can read a series that is stored as many files (`all_files=True`).** `load` took the last file that matched a series, which is right for the collaboration's processed files (one per series) and reads one dump of 30 for Run 76. With `all_files=True` every match is read, in name order (`files="~/goldsluice-output/r76-rq/{series}_F*.root"`), `data.files` maps the series to the list of files and the cache is stale if a dump is added or rewritten. New `find_files(series, files)`. Found by reading the processed Run 76 quantities back as RQs.

### Changed

- **The Run 76 readout has a 500-sample pretrigger window, not 1000 (issue 154); the readouts are now in `registry/readouts.toml`.** Measured on three dumps of `07221203_2025` (about 8,800 events): the trigger-locked pulses start at sample 480 to 520 and the trace is flat before, so the 1000-sample baseline of `peak` was about half pulse and `current_max` came out at 0.52 of its value (a baseline over samples 10 to 500 gives 0.999). `goldpan.config.DCRC_RUN76` and the registry's `[readouts.DCRC_RUN76]` now say 500 (also t = 0 of the time axis is now sample 500), so **the processed output of a definition that uses `readout = "DCRC_RUN76"` is redone on the next run** (the fingerprint changes; about 100 s for the 30 dumps of the series) and any `current_max` made before is too low by about half for the trigger-locked events. `registry/readouts.toml` holds `DCRC_RUN76` and `Z7` with their `status` and `evidence`; the presets of `goldpan.config` stay for existing code, and a test checks that they agree with the file. The `Z7` entry says it is not checked against a file: the ODB of series 24260424_145101 gives a different pre-trigger offset. The flat names for the existing notebooks (`pulse_config.PulseConfig()` and the defaults of `pulse_*`) keep the 1000-sample window they were run with, so those notebooks give the same numbers when run again.

### Added

- **`goldsluice/examples/r76-registry.dataset.toml` uses every algorithm of `goldsluice`.** Six steps (`peak`, `max_time`, `baseline`, `integral`, `excursion`, `rise_time`), nine quantities for each of the six channels, with every number taken from the readout (`@readout.*`) except `amps_per_adc` (still a placeholder) and the rise-time levels `lo = 0.1`, `hi = 0.9`. `r76.dataset.toml` keeps the two steps of the guides. **Because the definition changed, its fingerprint changed: a run with it processes the dumps again** (about 100 s for the 30 dumps of Run 76, longer with the extra steps' output to write). A new test checks that the example has a step for every algorithm, so a port that is not added to it fails the test (`PORTING.md` says so), and that every step runs with its parameters. Run on a real dump (F0005, 2,887 events): all nine quantities are written; 59 events of Side2pA have no rise time (`nan`).

- **`goldsluice`: the algorithm `rise_time` (issue 155, fourth port).** The 10-90 % rise time of the largest pulse of every trace (`rise_time_s`, `goldpan.algorithms.rise_time`): the time between the last samples before the peak that lie below `lo` and `hi` of its height above the baseline, `nan` where the trace has no positive peak or never lies below the `lo` level before it. The peak is the first largest sample of the whole trace (the glitch samples included, as in goldpan). `lo` and `hi` have no defaults and must satisfy `0 <= lo < hi <= 1`: a definition file writes them (`lo = 0.1`, `hi = 0.9` for the usual rise time). On a real dump (2,887 events, three channels) goldsluice and goldpan agree on every event, the `nan` ones included; 10,000 traces take 15.8 ms in Rust, about 540 times faster than the mirror. Not ported: `rise_sample`, `excursion_duration` and `half_max_time_us`, which are still under development in goldpan. Rebuild the extension to use it (`maturin develop --release` in `goldsluice/`).

- **`goldsluice`: the algorithms `integral` and `excursion` (issue 155, second and third ports).** `integral` is the sum of `x - baseline` over the whole trace times `sample_period_s` (the unit of the trace times seconds, as `goldpan.algorithms.integral`; the baseline is the mean of `glitch_samples` to `pretrigger_samples`). `excursion` gives `max_deviation`, the largest `|x - baseline|` after the window, and `excursion_ratio`, that divided by the window's standard deviation (`goldpan.quantities.max_deviation` and `excursion_ratio`, the "dev" and "ratio" of the noise-selection notebooks; a window with no scatter gives `inf` or `nan`, as in numpy, and a trace with no sample after the window is refused). Each has a Python mirror, a Rust kernel, an agreement test against the goldpan function and a batch test. The largest of a trace above its baseline, goldpan's `pulse_max`, is `peak`'s `current_max` with `amps_per_adc = 1`, so it needed no port. On a real dump the Rust results equal goldpan's: `max_deviation` exactly, `excursion_ratio` to 1e-14, `integral` to 3e-13 of the sum of the absolute deviations (a sum of terms of both signs: an event whose integral nearly cancels differs from numpy's pairwise sum by that rounding, which is a larger fraction of a small result). 10,000 traces of 4096 samples take 14.7 ms (`integral`) and 14.4 ms (`excursion`) in Rust, 450 and 650 times faster than the mirrors. Rebuild the extension to use them (`maturin develop --release` in `goldsluice/`).

- **`goldsluice`: the algorithm `baseline` (issue 155, the first port of the list).** The mean and the standard deviation of the pretrigger window of every trace, `baseline_mean` and `baseline_std` (the population deviation, in ADC counts; the same window, `glitch_samples` to `pretrigger_samples`, as `peak` uses for its baseline), with a Python mirror, a Rust kernel and a parity test against `goldpan.quantities.pretrigger_mean` / `pretrigger_std`, so the two packages cannot define it differently. The deviations are summed in a second pass, which stays accurate for a baseline large against its scatter. 10,000 traces of 4096 samples with the Run 76 window take 2.7 ms in Rust (`cargo bench`), 0.28 microseconds a trace, about 1,800 times faster than the mirror. Use it in a definition file with `algorithm = "baseline"`, `glitch_samples = "@readout.glitch_samples"` and `pretrigger_samples = "@readout.pretrigger_samples"`; the output of `goldsluice` needs the new `_core` built (`maturin develop --release` in `goldsluice/`).

- **`goldpan.rqdata`: the RQs of a whole list of series as numpy arrays, with a cache (issue 172).** `load(dataset, rqs)` has the call of the collaboration's `rqdata` (`data = load("24260424_145101", ["EventType", "PTOFamps", "P*max"])`, `data["PTOFamps"]`, `data.files`, `P*` for the phonon channels, a series name, a list of them or a CSV with a `series` column as the dataset), on top of `rq_root.read`. The read is saved in a folder of your own outside the repository (`$GOLDPAN_CACHE`, default `~/.cache/goldpan/rqdata`) and the next `load` of the same files reuses any cached read that contains all the RQs asked for. Unlike a cache keyed on file names, the key is the size and modification time of the files and the goldpan version, so a rewritten file is read again; entries are written atomically; `refresh=True`, `cache=False`, `cache_info()` and `cache_clear()`. Where the files are and which `zip<N>` tree to read are not in the library: `files=` / `GOLDPAN_RQ_FILES` (a pattern with `{series}`) and `detector=` / `GOLDPAN_RQ_DETECTOR`. Not yet: named datasets, `iterate`, a cache of traces (issue 172).

- **A registry for the detectors, outside the library (`goldpan.registry`, the folder `registry/`; issue 150).** What the analysis needs to know about a detector (its number, type, readout, and where each named channel is wired in a file format) is data, not code, so `goldpan` holds only the mechanism: records are TOML files in folders (any object with a `load()` method is a source, so a Git repository or a database can take a folder's place), every record must say its `status` (`confirmed` or `inferred`) and its `evidence`, unknown keys and a name defined twice are errors, and `registry.compare` checks a record against what a file says. A dataset definition names the folders with the new key `[dataset] registry = [...]` (or the environment variable `GOLDPAN_REGISTRY` does); a source whose `detector` is in the registry takes its readout, the defaults of `[sources.read]` for its file format and, for ROOT output, `root_detector` from the record, and anything written in the file wins key by key (a readout that disagrees with the registry's is a warning). A detector that is in no registry is a label, as before, and a definition that writes everything out has the fingerprint it had, so processed files are not redone. Definition format version 3. `registry/run76.toml` has the Run 76 detector `NAI-S2` (`number = 1` is our choice, the map is inferred, both said in its evidence); `goldsluice/examples/r76-registry.dataset.toml` is the example that uses it, and a test shows it means the same as `r76.dataset.toml`. `goldpan.adapters.midas.detectors(path)` lists what the begin-of-run ODB of a MIDAS file says about each of its detectors (`Det01` to `Det24`: name, type, tower, plane, the readout lengths including the pre- and post-pulse lengths of hybrid readout), and `midas.registry_entry` writes a starting registry entry from it.

- **A developer quick-sheet, "Running goldsluice and developing an algorithm" (`docs/developers/goldsluice-algorithm.pdf` and its web page).** Setup (Rust, and the Visual Studio Build Tools on Windows), running `peak`, timing it (`compare`, `cargo bench`), and the whole path of a new algorithm from the Python mirror to the Rust kernel, with the worked example `max_time` (actually built and tested before it was written down) and the traps it met. `goldsluice` itself: every algorithm's mirror now also defines `bad_cases()` (inputs both versions must refuse, with the same message), which the parity test uses instead of assuming a `pretrigger_samples` parameter, and `PORTING.md` warns about floats in error messages and NaN comparisons.
- **`goldsluice/`: the first step of the Rust reduction package, with one algorithm, `peak`.** `goldsluice.run("peak", traces, glitch_samples=..., pretrigger_samples=..., amps_per_adc=...)` returns the largest raw ADC value and the largest baseline-subtracted current (amps) of every trace, from a Rust kernel (parallel over traces with rayon) or, with `backend="python"`, from its Python mirror. Every algorithm has both, and `tests/test_parity.py` checks that they exist, agree on the standard inputs and refuse bad parameters alike; `goldsluice.compare` and `cargo bench` time them (on 20000 Run 76 traces of 4096 samples: about 29 ms in Rust against 15.7 s in Python on this PC). `goldsluice/PORTING.md` explains how to write a mirror in the *kernel subset* and port it to Rust. A workflow (`.github/workflows/goldsluice.yml`) builds and tests it on Windows, macOS and Linux. Not published to PyPI yet; no change to `goldpan`.

## [0.10.0] - 2026-10-26

**Students, please:** the library gained new parts and four new packages, so update: follow *Updating your setup* (student guide 7), Step 2 (bring in the newest changes) and Step 3 (`python -m pip install -r requirements.txt`), then run `python python/check_environment.py`, which should say `Environment OK`. Python is still 3.12, so you do not need a new environment. The new packages are `awkward`, `pyarrow`, `uproot` and `lz4`, and `goldpan` itself is now 0.2.0; until you reinstall, the check warns about them. Nothing you already run changes: the old names (`pulse_cuts` and the others) and your notebooks work as before, and no result changes.

The library `goldpan` can now read and write data, not only analyse it: an immutable container of one detector's events (`goldpan.data`), adapters for the idx dumps, the native Parquet format, the raw SuperCDMS SNOLAB DAQ files (`.mid`, `.mid.gz`, `.mid.lz4`) and the RQ files in ROOT, the RQ-only noise cuts and trace algorithms ported from `scdms-analysis-tools`, and a synthetic series in all four formats for testing. A new developer quick-sheet explains how to write an adapter, and a workflow can publish the library to PyPI (nothing is published by it yet).

`goldpan` 0.2.0: new modules `goldpan.data`, `goldpan.adapters` (`idx`, `parquet`, `midas`, `rq_root`, `rq`), `goldpan.rq_cuts`, `goldpan.algorithms` and `goldpan.testing`; the readout has no defaults in the package (the old flat names keep the Run 76 defaults); new optional extras `parquet`, `root` and `midas`; new dependency `awkward`. No result of an existing function changes.

### Added

- **`goldpan.data`: the immutable container of one detector's events (first step of the design of 2026-10-25/26).** `Events` holds a `Detector` (its name, `ChannelInfo`s with roles, and a `Readout` made of named `Segment`s, each with its own `PulseConfig`; only the default segment `main` is used so far, so that hybrid sampling later changes no signature or file), the read-only `traces` keyed by (channel, segment), the `quantities` as an Awkward Array with the event key fields `series`, `dump`, `event` and an optional `t_trigger`, and `meta`. `select`, `with_quantities`, `concatenate` and `time_axis` return new objects; the invariants are checked once, when it is built. No file format and no adapter yet (next: the idx and Parquet adapters). **New dependency: `awkward` (pinned 2.14.0 in `requirements.txt`)**, so existing environments need `pip install -r requirements.txt` (a *Students, please:* line at the next release; the library becomes 0.2.0). 20 tests in `python/tests/test_goldpan_data.py`.
- **`goldpan.adapters`: the idx and Parquet adapters (second step of the design of 2026-10-25/26).** `parquet` is the native format (reads and writes; its docstring is the specification, format version 1: one file per series and dump, plain Arrow types so other tools can read it, a `_goldpan.json` manifest, `iter_chunks` for datasets larger than memory), `idx` reads a dump of the NSDF archive into an `Events` (the readout and the channel map are given, never assumed), and `goldpan.adapters.register` / `goldpan.testing.check_adapter` let anyone add and test an adapter for another format. A small synthetic dataset is committed in `python/tests/data/sample_dataset/`. **New dependency: `pyarrow` (pinned 26.0.0 in `requirements.txt`)**, so existing environments need `pip install -r requirements.txt` (covered by the same *Students, please:* line as `awkward` at the next release). Tests in `python/tests/test_goldpan_adapters.py` and `test_goldpan_idx_adapter.py`; the library reference page lists the new modules.
- **`goldpan.rq_cuts` and `goldpan.algorithms`: the rq_cuts and trace algorithms of `scdms-analysis-tools`, ported (third step of the design of 2026-10-25/26).** `rq_cuts` has the RQ-only noise selection (`phonon_log_ratios`, `pileup_randoms`, `loose_randoms`, `tight_randoms`, `pt_std_proxy`, ...) and the calibration-line cut (`calibration_line`, `triggered_physics`; under development); channel names, thresholds, windows and the trigger detector are always passed in. `algorithms` has `lowpass` (zero-phase Butterworth with numpy, no scipy needed), `downsample`, `pulse_max`, `max_time`, `integral`, `rise_time` and `compute`, which adds quantities to an `Events`; they take a `config` like the rest of the package. No new dependency. Tests in `python/tests/test_goldpan_rq_cuts.py` and `test_goldpan_algorithms.py`.
- **Synthetic series in four formats, for testing the adapters (`python/tests/synthetic_series.py`).** One deterministic, made-up series (07221203_2025 layout: two dumps, three DCRC boards, the six Side-2 sensors, 4096 samples at 0.8 us; physics and random triggers and one pileup event) written as an idx dump (read with `nsdf_dark_matter` and our idx adapter), as SNOLAB MIDAS `.mid.gz` files (a writer and a reader following the CDMS I/O library's `pack_event`/`unpack_event`, format version 8, with a begin-of-run ODB), as RQ Parquet and RQ ROOT files (`rqDir/eventTree`, `rqDir/zip1`), and as a goldpan Parquet dataset. Generated on demand (nothing is committed); 12 tests in `python/tests/test_synthetic_series.py` check that every format holds the same events. The MIDAS files were checked against the library's source, not against a real DAQ file yet; the ROOT tests run only where `uproot` is installed (it joins `requirements.txt` with the uproot adapter).
- **`goldpan.adapters.rq_root` and `goldpan.adapters.rq`: the uproot adapter, for the RQs of the reconstruction (fourth step of the design of 2026-10-25/26).** `rq_root.read(path, detector=..., branches=[...])` reads `rqDir/eventTree` and `rqDir/zip<N>` of a ROOT file (or a list or folder of files) as a table of quantities with the event key first (`series`, `dump` as `F0003`, `event`); wildcards in `branches`, NaN for a missing branch, `iter_chunks`, and no default detector number (the port of `rqdata`, without its collaboration paths or datasets). `rq.attach(events, table)` joins such a table to an `Events` on the key. **New dependency: `uproot` (pinned 5.7.7 in `requirements.txt`, extra `root`)**, so existing environments need `pip install -r requirements.txt` (the same *Students, please:* line as `awkward` and `pyarrow`). 12 tests in `python/tests/test_goldpan_rq_root.py`, on the synthetic series; the ROOT checks of the synthetic series now run in CI too.
- **`goldpan.adapters.midas`: the MIDAS adapter, for the raw SuperCDMS SNOLAB DAQ files (fifth step of the design of 2026-10-25/26).** `midas.read(path, detector_name=, detector_id=, channels={name: number}, config=)` reads `.mid`, `.mid.gz` and `.mid.lz4` files into an `Events` (format versions 4 to 8 of the CDMS I/O library; the traces stay `uint16`), with `series`/`dump` from the file name, the event number, trigger ID, trigger type as text, readout type and global timestamp as quantities, and the run number, start/stop time (begin- and end-of-run ODB), `complete` and the number of skipped events in `meta`. The readout is never assumed: its sample period is checked against the file. Polling-cycle and veto-only events are skipped, `max_events=` and `iter_chunks` limit what is read, and a file cut short ends without an error (`complete` False). Verified on a real Z7 file (24260424_145101: 17 trigger events and the begin- and end-of-run ODBs), via two optional samples (`GOLDPAN_MIDAS_SAMPLE`, `GOLDPAN_MIDAS_TAIL`; real data, not committed); the synthetic MIDAS files now have the real layout too (veto-only and polling events, end-of-run event, `Runinfo`, run-number serial). Hybrid sampling is not read yet (a clear `NotImplementedError`). **New dependency: `lz4` (pinned 4.4.5 in `requirements.txt`, extra `midas`)**, so existing environments need `pip install -r requirements.txt` (the same *Students, please:* line as `awkward`, `pyarrow` and `uproot`). 14 tests in `python/tests/test_goldpan_midas.py`.
- **A developer quick-sheet, "Writing an adapter" (`docs/developers/writing-an-adapter.pdf` and its web page; last item of step 3 of the design of 2026-10-25/26).** Two pages: the two shapes of an adapter (events, or a table of quantities), the rules all four existing adapters follow (the user names the detector, channels and readout; check what the file knows; the key is series, dump, event; skip and count, never invent), the three functions (`read`, `iter_chunks`, `write`), how to test one with `check_adapter` and the synthetic series, how to register it or add it as a built-in, and what the real MIDAS file taught. The example in it is a complete, tested adapter (`python/tests/example_adapter.py`, 4 tests in `test_example_adapter.py`). Writing the example found a fault in `goldpan.testing.check_adapter`, now fixed: its round-trip step read the written file back without the keyword arguments of the call, so an adapter that needs the detector name or the readout from the user could never pass; it now passes the same arguments. The guide is added to `build.sh` and to the front page.
- **A workflow that publishes the library to PyPI as `goldpan` (`.github/workflows/publish-goldpan.yml`; item 33 of the task list).** A tag `goldpan-vX.Y.Z` builds the package, installs the wheel in a clean environment, imports every module and, after the maintainer approves the `pypi` environment, uploads it; PyPI trusts the workflow, so no token is stored anywhere. ## [0.2.0] - 2026-10-07

Developer and student quick-sheets, a safer note-publishing pipeline, and guidance for updating notes.

### Added

- `docs/developers/note-creation.pdf` and `docs/developers/note-creation-ai.pdf`: two one-page developer quick-sheets, for creating a hand-written note (notebook, figures, page, index row, pinned links, PR) and for doing it with an AI agent (a starting brief, what the agent may and must never do, the checks you still do yourself). Both also cover reviewing a student note. Linked from the front page under "Developer guides". Sources and the figure script are in `docs/developers/src/`.
- `docs/students/note-cheatsheet.pdf`: a one-page student cheat-sheet, "From note to live page", that summarises and links to guides 3 and 4 (the commands, a checklist, what the PR check's messages mean). Linked from the front page. Source in `docs/students/src/`.
- `docs/developers/developer-workflow.pdf`: a one-page developer workflow (the daily pull request loop, how branches relate, releases), linked from the front page under "Developer guides". Source and figure script in `docs/developers/src/`.
- `tools/build_notes.py` removes generated student pages and figures whose note has been deleted (and figures no longer in `notes/src/img`), so deleting a note's source is enough to take it off the site. Found while removing the pipeline test note, which needed its generated files deleted by hand.

### Fixed

- Updating a published student note: guide 4 and the student cheat-sheet now say to run `git pull origin develop` first and to keep the note's S-number. A student's old branch still said `id: "TBD"`; the PR check accepts that, but the build refuses it, so the note's update could not be published and the maintainer had to catch it before merging. The developer quick-sheet "Creating a note" now covers updating a note, and warns reviewers to check for `TBD`.
- `tools/build_notes.py` now passes text to pandoc as UTF-8. On Windows it used the system code page, which garbled non-ASCII characters (an em dash, `µ`) in a note when it was built locally. The Linux build that publishes notes was not affected.

### Changed

- The "Check instructions" workflow also runs on pushes to `develop`, so every merge into the branch the site is served from is checked.

## [0.1.0] - 2026-10-07

First release. It gathers the state of the repository when semantic versioning and Git Flow began.

### Added

- `python/`: the shared pulse-analysis library (`pulse_quantities`, `pulse_cuts`, `pulse_operations`, `pulse_io`, `pulse_archive`), with `@status` tagging and a synthetic-data test suite (52 tests).
- `R76/analysis_notes/`: exploratory notebooks for series `07221203_2025` (Run 76), and `archives/` for selected event ids.
- The notes site on GitHub Pages: notes 1, 1a, 2, 2a and 3 to 7, with the index, a status legend and notebook-deprecation policy.
- Student guides (PDFs in `docs/students/`, built from `docs/students/src/`): setup and first analysis for Windows, macOS and Linux; writing a note; publishing a note; publishing with an AI assistant; working in the browser with GitHub Codespaces. A dev container for Codespaces.
- Student-notes publishing: Markdown sources in `notes/src/`, the validator and builder `tools/build_notes.py`, and a GitHub Action that checks pull requests and builds the pages.
- A "Check instructions" workflow that repeats the setup and first-analysis steps on Windows, macOS and Linux.
- `AGENTS.md` and `CLAUDE.md` (project rules for contributors and AI agents), a pull request template, `.github/CODEOWNERS`, `RELEASING.md`, and this changelog.
- `requirements.txt`, listing the pinned package versions.

### Changed

- Student guides are at setup version 8 and first-analysis version 6: direct Miniforge download links, installer options spelled out, plain-language explanations of each command, Command Prompt before the Miniforge Prompt on Windows, `jupyterlab` installed, and the data downloaded from the home folder.
- The notes site and student guides are served by GitHub Pages from `develop` (`/docs`), so guide fixes and notes are live on merge and do not wait for a release. The student-notes workflow builds on pushes to `develop` as well as `master`. Guides 1, 3, 4, 5 and 6 now say `develop` where they named `master`.
- Pull request reviews: GitHub requests only the maintainer automatically (`.github/CODEOWNERS`); other reviewers are added by hand. The maintainer may merge their own pull requests.

### Removed

- `environment.yml` (replaced by `requirements.txt`; the guides use explicit install commands).

### Fixed

- The pinned `nsdf-dark-matter-cli` version: 0.3.1 does not exist on PyPI; 0.5.0 is the working version.
